# Production infrastructure and remaining backend/frontend modules

This change adds the production deployment stack (Dockerfile, docker-compose, deploy script, backup script, seed, admin creation, CSV import) and builds out six new backend modules (notas, diario, estagios, financeiro, requerimentos, atas) with their corresponding frontend pages. It also replaces mock data in four existing frontend list pages with real API calls via a `useApi` hook. The security layer adds helmet, rate limiting, and zod validators, while a Prisma migration defines the full schema for all new domain tables.

**Watch for:** Validators are defined but never wired into routes (confirmed). Rate limiting on `/api/auth` is applied after the global `/api` limiter so both fire on auth endpoints, which may confuse operators (confirmed). The frontend `docker-compose` references a Dockerfile that does not exist in this diff (confirmed). The seed and `create-admin` scripts log plaintext credentials to stdout (confirmed). Several frontend pages call incorrect or non-existent API endpoints (likely).

## High-level view

The deployment stack is a standard Docker Compose arrangement with a multi-stage Node build and a deploy shell script. It assumes a frontend Dockerfile exists at `src/frontend/Dockerfile` which is not included in this diff, so `docker compose up` will fail out-of-the-box.

Security middleware is wired into the Express app at the top level, but the Zod validation schemas in `validators/index.ts` are never imported by any route file. Every route accepts arbitrary JSON bodies today because `validateBody()` is not called anywhere. This is the largest gap in the change.

The six new backend modules follow an identical structure: controller with manual `if (!req.user)` guards and inline param checks, a service class that queries Prisma with tenant isolation and soft-delete filtering, and a route file that applies `authMiddleware` at the router level. The financial module is the most complex, with bulk payment generation and reporting endpoints.

Frontend pages mix two patterns: pages that were converted from mock data to API calls (alunos, cursos, turmas, matriculas) and newly-created pages for the new modules. Many new pages (chamadas, lancamento de notas) call API endpoints that don't correspond to existing routes and still use hardcoded select options rather than fetching them from the backend.

Tests exist for all six new services but are purely unit-level mocks of Prisma. No integration or API-level tests verify that the routes, middleware, and services compose correctly.

## Validator schemas defined but never applied

The `validators/index.ts` file defines Zod schemas for every domain entity (login, student, course, class, enrollment, grade, attendance, diary entry, internship, request, minutes, financial account, financial payment). The `validateBody` function in `security.ts` is the intended middleware to use them. However, no route file imports either the schemas or the middleware. Every POST and PUT handler receives `req.body` unvalidated.

```typescript
// security.ts exports this:
export function validateBody(schema: ZodSchema) { ... }

// No route file does this:
import { validateBody } from '../middleware/security';
import { gradeSchema } from '../validators';
router.post('/', validateBody(gradeSchema), (req, res, next) => ...);
```

The controllers do inline checks (`if (!req.body.studentId)`) which partially compensate for missing validation, but they don't check types, don't sanitize strings, and don't catch malformed UUIDs. The Zod schemas exist to do exactly this; they just need to be wired in. **Confidence: confirmed.**

## Docker Compose frontend service references missing Dockerfile

The compose file declares:

```yaml
frontend:
  build:
    context: ./src/frontend
    dockerfile: Dockerfile
```

No `src/frontend/Dockerfile` is included in this diff. The frontend directory has a `vercel.json` suggesting Vercel deployment, but the compose file expects a Docker build. Running `docker compose up` will fail with a "Dockerfile not found" error. **Confidence: confirmed.**

## Rate limiting overlap on auth routes

In `server.ts`:

```typescript
app.use('/api', rateLimitMiddleware);          // 100 req / 15 min
app.use('/api/auth', authRateLimitMiddleware); // 5 req / 15 min
```

Express applies middleware in registration order, so requests to `/api/auth/login` hit both limiters. After 5 login attempts the auth limiter blocks, but the global limiter's counter is also incrementing. This isn't a bug per se, but it means the 6th login attempt could return either a 429 from the global or the auth limiter depending on timing, with different error messages. More importantly, every auth request burns one slot from the global 100-request budget, which could matter for small rate-limit windows in multi-tenant scenarios. **Confidence: confirmed.**

## Seed credentials in logs

`seed.ts` outputs:

```
CREDENCIAIS DO ADMINISTRADOR:
Email: admin@sistema.com
Senha: Admin@123
Tenant ID: <uuid>
```

When deploy.sh runs `npx ts-node prisma/seed.ts` inside the container, this goes to Docker's log driver. In production with centralized logging (CloudWatch, Datadog), plaintext passwords end up in searchable log stores. The `create-admin.ts` script has the same issue, though it's typically run manually. **Confidence: confirmed.**

## Frontend pages calling wrong API paths

`ChamadasPage` initializes with `useApi<StudentAttendance[]>('/diario')`. The backend has no `GET /api/diario` endpoint at the router root; the diary routes are `/diario/entries` and `/diario/attendance`. The page will receive a 404 or a 500 depending on how the frontend error boundary handles it.

Similarly, `LancamentoNotasPage` calls `useApi<StudentGrade[]>('/notas/lancamento')` but no such route exists; grades are listed at `GET /notas` with query filters. These pages will fail to load data in production. **Confidence: likely** (confirmed for the route definitions; the actual API prefix depends on how the frontend hook prepends the base URL).

## Financial bulk payment date arithmetic

The `bulkCreatePayments` method increments months using `setMonth`:

```typescript
const dueDate = new Date(startDate);
dueDate.setMonth(dueDate.getMonth() + (i - 1));
```

This is a shared `Date` object being mutated in a loop, but it's re-created each iteration so that's fine. However, `setMonth` has the well-known month-overflow behavior: starting from January 31, `setMonth(1)` yields March 3 (because February 31 doesn't exist). For a tuition payment system this means some installments may land on unexpected dates. **Confidence: confirmed** (the code is visible; the impact depends on whether `startDate` is ever late in a month).

## Test coverage shape

Each new service has a test file with 7-10 test cases covering the happy path for CRUD operations, error cases for not-found entities, and filter/pagination behavior. All tests mock Prisma at the module level. No test exercises the controller or route layer, so authentication middleware, parameter parsing, and error propagation through Express are untested. The existing modules (cadastros, matriculas) had no test changes. The frontend has zero test coverage in this diff.
