# Six educational management modules (Notas, Diario, Estagios, Financeiro, Requerimentos, Atas)

This change adds the full backend (services, controllers, routes) and frontend (Next.js pages) for six new modules in the SaaS educational platform, all following the same multi-tenant, Prisma-backed pattern established by existing modules. Every module uses tenant-scoped queries, soft deletes, paginated list endpoints, and the shared auth middleware. The frontend pages are currently wired to mock data rather than the API.

Watch for: Protocol number generation in Requerimentos has a race condition under concurrent requests (confirmed). The `getCashFlow` report in Financeiro loads all payment records into memory without pagination or date bounds, which will degrade as data grows (confirmed). No role-based access control is enforced on any of the new endpoints — authentication is present but authorization is absent (confirmed).

## High-level view

All six modules share the same structural skeleton: a service class encapsulating Prisma queries behind tenant isolation, a controller that validates a few required fields and delegates, a route file that applies `authMiddleware` as a blanket guard, and frontend pages displaying hardcoded mock data. The design is consistent, but it also means the same gaps are replicated across every module.

The financial module is the most complex addition, with accounts, payments, bulk installment generation, overdue reports, and a cash-flow summary. The cash-flow report fetches an unbounded dataset into memory. The overdue report relies on records already being marked `OVERDUE` rather than computing overdue status from due dates, meaning a separate job or trigger is needed to keep the data accurate.

Requerimentos introduces auto-generated protocol numbers (`REQ-{year}-{sequential}`), but the sequence derivation via `count()` is not concurrency-safe and can produce duplicates under parallel requests.

Frontend pages across all six modules render mock data inline and perform no API calls. Forms validate locally and show a success toast without persisting anything. This is UI scaffolding, not functional integration.

<summary>Issues (7)</summary>

1. **Requerimentos protocol race condition** — Protocol generation uses `count()` to derive the next sequence number. Two concurrent creates can get the same count and produce duplicate protocols. Use a database sequence or unique constraint with retry logic.
2. **Financeiro unbounded getCashFlow query** — Loads every payment for the tenant into memory with no date filter or pagination. Add date-range parameters or use database aggregation.
3. **No role-based authorization** — All new routes only check authentication (valid JWT), not whether the user's role permits the operation. A student token can create grades, approve requests, or modify financial records. Add role checks at the route or controller level.
4. **Overdue status is static, not computed** — The overdue report filters `status: 'OVERDUE'` but nothing in this change transitions a payment from PENDING to OVERDUE when the due date passes. Either compute overdue dynamically or document the required background job.
5. **Frontend pages are non-functional** — All pages use inline mock data and never call the backend. Forms "succeed" without persisting. This is scaffolding, not integrated UI.
6. **Bulk operations lack transactionality** — `bulkCreateAttendance`, `bulkCreate` (notas), and `bulkCreatePayments` use `createMany` without wrapping in a transaction. Partial failures will leave orphaned data.
7. **Input validation is minimal** — Controllers check 1-2 required fields but don't validate types, ranges (negative amounts, grades > 10), or format (dates). Malformed input reaches Prisma, which may throw unstructured errors.

## Protocol generation race in Requerimentos

The `RequerimentosService.create` method derives the next protocol number by counting existing requests:

```typescript
const count = await prisma.request.count({ where: { tenantId } });
const protocol = `REQ-${year}-${String(count + 1).padStart(5, '0')}`;
```

Two concurrent requests that read `count` before either commits will both compute the same protocol value. The `protocol` field in the schema has no `@unique` constraint, so both inserts succeed silently with duplicate numbers. The fix is either a database-level sequence, an auto-increment column, or a unique constraint combined with retry-on-conflict logic.

## Financial module: unbounded data loading

`getCashFlow` fetches every `FinancialPayment` for the tenant and sums amounts in application memory:

```typescript
const payments = await prisma.financialPayment.findMany({
  where: { tenantId, deletedAt: null },
  orderBy: { dueDate: 'asc' },
});
```

For an institution with thousands of students and years of payment history, this query returns an arbitrarily large result set. The same pattern appears in `getOverdueReport` but is less severe because the `OVERDUE` status filter limits the result set. `getCashFlow` has no such filter — it loads PENDING, PAID, and OVERDUE records alike.

## Authorization model: authentication without authorization

The auth middleware extracts `userId`, `tenantId`, `email`, and `roleId` from the JWT, but no downstream code checks `roleId`. Every route under `/notas`, `/financeiro`, `/requerimentos`, etc. is accessible to any authenticated user in the tenant. In an educational system this means a student token (if one is issued) could POST to `/notas/bulk`, PATCH request statuses, or create financial accounts. The `roleId` field is present in the payload — the enforcement layer is simply missing.

## Overdue detection gap in Financeiro

The overdue report queries:
```typescript
where: { tenantId, deletedAt: null, status: 'OVERDUE' }
```

Nothing in the new code ever transitions a payment from `PENDING` to `OVERDUE`. The `updatePayment` endpoint allows manually setting status, but there's no automated mechanism (cron job, database trigger, or query-time computation). Until that mechanism exists, the overdue report will always return an empty set for newly created payments that pass their due date.

## Bulk operations without transactions

`bulkCreatePayments` in Financeiro creates N payments via `createMany`. If the database connection drops mid-write, some payments are created and others are not, leaving the account in an inconsistent state (e.g., 3 of 6 installments exist). The same applies to `bulkCreateAttendance` and `bulkCreate` in Notas. Wrapping these in `prisma.$transaction` would make them atomic.

## Input validation gaps

Controllers perform presence checks only:
```typescript
if (!req.body.studentId || !req.body.classId || !req.body.disciplineId) {
  throw new AppError('studentId, classId and disciplineId are required', 400);
}
```

No type coercion, range validation, or format checking occurs. A negative `totalAmount`, a `value` of 999 on a grade, or an `installments` value of 0 will pass through to Prisma. In the financial module, `installments: 0` produces a loop that doesn't execute but creates no payments — silently returning `count: 0` without error.
